# ACP (Agent Client Protocol) for Zed - research

Date: 2026-10-17. Status: research only, no code. Sources are cited inline;
claims without a citation are our own inference (marked INFERENCE).

## Research

**What ACP is.** The Agent Client Protocol is Zed Industries' open standard
(JSON-RPC 2.0 over stdio, newline-delimited) that lets any coding agent plug
into any editor - the "LSP for AI coding agents". Zed created it in August
2025; JetBrains joined shortly after; the ACP Registry (agent directory built
into both editors) launched January 2026. ~50 agents implement it (Claude
Code, Codex CLI, Gemini CLI, Copilot CLI, OpenCode, Goose, Qwen Code, …).
Apache-2.0 licensed; official SDKs exist for Rust (`agent-client-protocol`
crate), TypeScript, and Kotlin. v1 is the stable wire protocol; v2 is a
published draft - production code should speak v1.
(Sources: dev.to/dmaxdev, dev.to/alextdev, byteiota.com, acpserver.org)

**Transport & lifecycle.** The editor spawns the agent as a subprocess and
talks over stdin/stdout. Sequence: `initialize` (capability negotiation, e.g.
`clientCapabilities.fs`, `terminal`) → `session/new` (with `cwd`, MCP
servers) → `session/prompt` (user message) → agent streams back via
`session/update` notifications → `PromptResponse` with a stop reason
(`end_turn`, `cancelled` via `session/cancel`).
(Sources: dev.to/alextdev, deepwiki rust-sdk getting-started)

**Method map (verified from rust-sdk + ai.zenheart.site):**
- Client → Agent (requests): `initialize`, `authenticate`, `session/new`,
  `session/load`, `session/resume`, `session/close`, `session/list`,
  `session/delete`, `session/prompt`, `session/set_mode`, `logout`
- Client → Agent (notification): `session/cancel`
- Agent → Client (request): `session/request_permission` (options
  `allow_once`/`allow_always`/`reject_once`/`reject_always`)
- Agent → Client (notifications): `session/update` carrying
  `agent_message_chunk`, `tool_call`, `tool_call_update`, `plan`,
  `available_commands_update`, `current_mode_update`
- Agent → Client (capability-gated): `fs/read_text_file`,
  `fs/write_text_file`, `terminal/*`, `elicitation/create`

**How Zed discovers agents.** Either the ACP Registry (default install path in
Zed v0.221.x+) or manual `agent_servers` in Zed's `settings.json`:
`{"agent_servers": {"zencode": {"command": "zencode", "args": ["acp"]}}}`.
(Source: agentty.org blog - same pattern: one engine, two front doors.)

**Precedent: agentty 0.2.0.** A single-binary terminal agent added `agentty
acp` speaking ACP over stdio - same engine, same tool registry, same
permission policy, just driven over JSON-RPC instead of a TUI. Sessions
persist to the same on-disk store so Zed's `session/load` replays them.
(Source: agentty.org) This is exactly the shape our integration should take.

## Ideas

**DesktopEvent → `session/update` mapping (INFERENCE, our design):**
| DesktopEvent (schema v1) | ACP update |
|---|---|
| `TextDelta` / `AssistantMessage.text` | `agent_message_chunk` |
| tool call start | `tool_call` |
| `ToolResult` | `tool_call_update` |
| `PermissionDenied` / PreToolUseHook deny | `session/request_permission` |
| plan-mode steps (PR #36) | `plan` |
| `ApiRetry`, `CompactBoundary`, verify attempts | (no direct ACP update; fold into `agent_message_chunk` as status text) |
| `SystemMessage` | `agent_message_chunk` (user-visible) or drop |

**Tool execution.** Two options: (a) agent calls tools directly and reports
via `tool_call`/`tool_call_update` (simplest, keeps our `:free`-only model
guard + RateGate in the loop); (b) delegate to Zed via `fs/*` and
`terminal/*` (editor mediates access, better UX, but our permission/hook
policy must be re-implemented as `session/request_permission`). Recommend (a)
for phase 2, (b) as a later option. (INFERENCE)

**Sessions.** We already persist sessions (`~/.zencode/sessions/<id>.ndjson` +
`index.json`, PR #30) - `session/list` and `session/load` (replay NDJSON as
`session/update` notifications) are a small adapter. `session/resume`
(reconnect without replay) maps to our in-memory session handle. (INFERENCE)

**Effort estimates (INFERENCE):**
| Piece | Size | Notes |
|---|---|---|
| stdio JSON-RPC framing + `initialize`/`session/new`/`session/prompt`/`session/cancel` | M | use official `agent-client-protocol` Rust crate |
| `agent_message_chunk` streaming from TextDelta | S | we already stream |
| `tool_call`/`tool_call_update` from engine events | M | direct mapping |
| `session/request_permission` ↔ PreToolUseHook | M | hook already exists (PR #8) |
| `session/list`/`load`/`resume` over session_store | S | PR #30 exists |
| `fs/*` + `terminal/*` delegation | L | policy duplication risk; defer |
| Registry listing + docs | S | |

**Free-model fit.** ACP is transport-only; our `:free`-only model guard and
RateGate live inside the engine, so Zed users get the same free-only
behavior. No protocol conflict. (INFERENCE)

## Results

**Phased plan:**
- **Phase 1 - read-only ACP agent (M):** `zencode acp` speaks v1;
  `initialize`, `session/new`, `session/prompt`, `session/cancel`;
  streams `agent_message_chunk`; tools disabled (prompt returns text +
  plan only). Proves the Zed integration end-to-end.
- **Phase 2 - full tool support (L):** `tool_call`/`tool_call_update`,
  `session/request_permission` wired to PreToolUseHook, `session/list`/
  `load`/`resume` over our session store.
- **Phase 3 - polish (M):** ACP Registry listing, `session/set_mode`
  mapping to plan mode, docs.

**Open questions for Z App:**
1. Direct tool execution (option a) vs delegating to Zed's `fs/*`/`terminal/*` (option b) - which matches our trust model?
2. Should `zencode acp` share the process with the Tauri backend, or be a standalone binary like agentty's approach?
3. Do we target the ACP Registry at launch, or manual `agent_servers` config first?

**Verified vs inferred:** protocol methods, transport, registry, Zed config
format, SDK languages, and v1/v2 status are verified from the cited sources.
The DesktopEvent mapping, effort sizes, and phased plan are our inferences
for Z App's review.
